Sentinel Oracle -- Merge Authority Isolation

Physically isolated merge authorization server. The workstation that develops code never holds the credentials to merge it. Even a fully compromised workstation cannot authorize a merge. Runs on a separate device on your local network with no cloud dependency.

# Architecture Overview

Sentinel Oracle implements a three-device trust model that separates development (workstation), authority (oracle server), and identity (phone). The oracle server is the only component with GitHub credentials capable of merging PRs. The workstation only has read-only access to the oracle dashboard. The phone provides biometric identity verification via WebAuthn.

THREE-DEVICE TRUST MODEL
|
[1] WORKSTATION (untrusted)
|-- Runs: sentinel-cli, IDE, git
|-- Access: Dashboard (read-only), GitHub API (read-only)
|-- Cannot: Merge PRs, modify oracle config, access oracle secrets
|
[2] ORACLE SERVER (trusted authority)
|-- Runs: sentinel-oracle daemon, Web server, SQLite, Tailscale
|-- Access: GitHub API (write -- merge permission), WebAuthn credentials
|-- Storage: HMAC signing keys, device registry, audit log (SQLite)
|-- Network: Local network only (Tailscale), no public ports
|
[3] PHONE (identity proof)
|-- Runs: Browser with WebAuthn/passkey support
|-- Access: /authorize endpoint (challenge-bound, TTL 45s)
|-- Authentication: Biometric (Face ID, fingerprint) or PIN
|-- Registration: One-time enrollment via admin dashboard
|
NETWORK TOPOLOGY
|-- All three devices communicate over Tailscale (WireGuard)
|-- Oracle server: accessible at oracle.tailnet-name.ts.net:3000
|-- No port forwarding, no reverse proxy, no cloud ingress
# Authorization Flow

Every merge requires a complete 6-step chain: developer creates PR, oracle detects it, workstation requests authorization, oracle generates QR challenge, phone authenticates via WebAuthn, oracle executes the merge. Each step is cryptographically bound to the specific PR number.

[1] DEVELOPER WORKSTATION
Developer pushes commits and creates a pull request on GitHub
GitHub runs CI checks (including Sentinel scan via GitHub Actions)
|
[2] ORACLE SERVER (POLL LOOP)
Every 10s: polls GitHub for PRs with status "merge-ready"
New PRs are added to the pending queue in SQLite
|
[3] WORKSTATION DASHBOARD
Developer opens http://oracle.tailnet-name.ts.net:3000/dashboard
Dashboard shows: PR number, title, author, status, timestamp
Developer clicks "Authorize" next to the target PR
|
[4] QR CHALLENGE (SERVER-SIDE)
Oracle generates: challenge = HMAC-SHA256(pr_number + nonce + expiry)
Renders QR code containing: authorize URL + challenge
TTL: 45 seconds. QR is one-time use (consumed on first submission)
|
[5] PHONE (WEBAUTHN)
Developer scans QR with phone camera
Phone opens /authorize?challenge=<hmac>&pr=<number>
Phone prompts biometric authentication (Face ID / fingerprint)
Phone creates WebAuthn assertion: { credentialId, signature, authenticatorData }
Phone POSTs assertion + challenge to /confirm
|
[6] ORACLE SERVER (MERGE EXECUTION)
Verifies WebAuthn assertion against stored credential public key
Verifies challenge HMAC (rejects if expired >45s or already consumed)
Verifies challenge is bound to this specific PR number
Calls POST /repos/<owner>/<repo>/pulls/<number>/merge via Octokit
Updates GitHub commit status to "success"
Logs to audit trail: timestamp, PR, device ID, challenge hash
# Hardware Requirements

The oracle server must be a physically separate device that stays online 24/7. It does not need a monitor, keyboard, or GPU -- only power and network connectivity. Recommended hardware options:

Device Specs Power Notes
Raspberry Pi 4/5 2GB+ RAM, 32GB SD 5W Official recommendation. Runs Node.js 18+ natively (arm64). Silent, low cost.
Intel NUC 4GB+ RAM, 128GB SSD 15W Higher margin for additional services. Can run Docker.
Mini PC (x86) 4GB+ RAM, 64GB+ storage 10-20W Any x86_64 Linux board. Must run 24/7.
Old laptop 4GB+ RAM, any storage 20-40W Overkill but works. Keep plugged in and closed.
# Tailscale Configuration

Tailscale is the required networking layer for Sentinel Oracle. It provides a zero-configuration WireGuard mesh network between all three devices. No ports are exposed to the public internet. All traffic flows through encrypted WireGuard tunnels authenticated by Tailscale's device identity system.

Why Tailscale

Sentinel Oracle uses Tailscale as its network transport because: (1) automatic NAT traversal via DERP relays, (2) device identity via Tailscale auth keys (replaces VPN credentials), (3) MagicDNS assigns stable hostnames (oracle.tailnet-name.ts.net), (4) ACLs provide fine-grained access control between devices, (5) no port forwarding or reverse proxy required. If Tailscale is not an option, you may substitute any WireGuard mesh network, but Tailscale is the only officially supported configuration.

Step 1: Install Tailscale on all three devices
# Raspberry Pi / Linux (oracle server, workstation)
$ curl -fsSL https://tailscale.com/install.sh | sh

# Verify installation
$ tailscale version

# Phone (iOS or Android)
# Install from App Store / Google Play Store
Step 2: Authenticate and join the tailnet
# On each device, run and follow the browser auth URL
$ sudo tailscale up

# Verify connection
$ tailscale status
# 100.x.x.x  oracle-server    username@ machine-name  linux  active; direct
# 100.x.x.x  workstation      username@ machine-name  linux  active; relay
# 100.x.x.x  phone            username@ machine-name  ios    active; direct
Step 3: Enable MagicDNS (one-time per tailnet)
# Go to https://login.tailscale.com/admin/dns
# Enable "MagicDNS" and set a tailnet name (e.g., "sentinel")
# Now devices are reachable at:
#   oracle-server.sentinel.ts.net:3000
#   workstation.sentinel.ts.net
#   phone.sentinel.ts.net (phone clients don't serve)

# Verify MagicDNS resolution from the workstation:
$ ping oracle-server.sentinel.ts.net
# PING oracle-server.sentinel.ts.net (100.x.x.x) ...
Step 4: Configure Tailscale ACL for least-privilege access
# Edit ACL at https://login.tailscale.com/admin/acls
# File: tailnet-policy.json (example below)

{
  "acls": [
    // Workstation can only reach oracle on port 3000
    {"action": "accept", "src": ["tag:workstation"], "dst": ["tag:oracle:3000"]},

    // Phone can reach oracle on port 3000 (authorization endpoint)
    {"action": "accept", "src": ["tag:phone"], "dst": ["tag:oracle:443"]},

    // Oracle can reach GitHub API (outbound only, no inbound from internet)
    {"action": "accept", "src": ["tag:oracle"], "dst": ["*:443"]},

    // Block all other inter-device traffic
    {"action": "accept", "src": ["autogroup:member"], "dst": ["autogroup:member:22"]}
  ],
  "tagOwners": {
    "tag:oracle":      ["username@github"],
    "tag:workstation": ["username@github"],
    "tag:phone":       ["username@github"]
  }
}
Step 5: Use an auth key for unattended operation (oracle server)
# Generate an auth key at https://login.tailscale.com/admin/settings/keys
# -- reusable=true, ephemeral=false, tags=tag:oracle

# On the oracle server, reauthenticate with the auth key:
$ sudo tailscale up --authkey tskey-auth-xxxxxxxxx --accept-dns=false

# The oracle service will now reconnect automatically after reboot
# via systemd: tailscale-autoconnect.service
Step 6: Verify end-to-end connectivity
# From workstation, verify oracle is reachable:
$ curl -s http://oracle-server.sentinel.ts.net:3000/health
# {"status":"ok","version":"1.0.0","uptime":123456}

# From phone browser, open the oracle dashboard:
$ http://oracle-server.sentinel.ts.net:3000/dashboard
# (Requires phone to be on Tailscale via the Tailscale app)
# WebAuthn Device Registration

WeAuthn (Web Authentication API) is the standard used for biometric identity verification. Each phone must be registered as an authenticator device before it can authorize merges. Registration is a one-time process that binds the phone's public key to the oracle's device registry.

Register a phone as an authenticator
# On the oracle server, start the admin registration endpoint:
$ sentinel oracle admin register-device --name "iphone-user"

# Output:
# Registration URL: http://oracle-server.sentinel.ts.net:3000/register/abc123
# TTL: 120 seconds

# Open the URL on the phone (must be on Tailscale)
# Phone prompts: "Do you want to register a passkey for Sentinel Oracle?"
# Authenticate with Face ID / Touch ID / fingerprint
# On success: "Device registered. You can now authorize merges."

Registration Data Stored

  • Credential ID (WebAuthn)
  • Public key (ECDSA P-256)
  • Device label (user-provided)
  • Registration timestamp
  • Last used timestamp
  • User agent string

Device Revocation

  • Revoke from admin dashboard
  • Immediately removes credential from registry
  • Logged to audit trail
  • Remaining devices unaffected
  • No re-enrollment needed for other devices
# Emergency Lockdown

The emergency lockdown is a global kill switch that immediately halts all pending and future merge operations. It is designed for incident response scenarios: compromised workstation,离职 developer, active supply chain attack, or any situation where merges must stop immediately.

Activation Effects

  • All pending QR challenges are invalidated
  • All pending PRs in the queue are rejected
  • GitHub commit status set to "failure" on all pending PRs
  • New /authorize requests return HTTP 403
  • Registration endpoint disabled
  • State persisted to SQLite (survives reboot)

Deactivation

  • Requires physical access to the oracle server
  • Run: sentinel oracle admin lockdown disable
  • Or log in via local console and disable via dashboard
  • Cannot be deactivated remotely (by design)
  • Deactivation is logged to the audit trail
# Lockdown CLI commands
$ sentinel oracle admin lockdown status
# {"active": false, "activatedAt": null, "pendingPRs": 3, "deviceCount": 2}

$ sentinel oracle admin lockdown enable
# Lockdown activated. All pending PRs rejected. New authorizations blocked.

$ sentinel oracle admin lockdown disable
# Lockdown deactivated. System resuming normal operation.
# Installation

Sentinel Oracle runs as a Node.js daemon on the oracle server. It is distributed separately from sentinel-cli via the sentinel-oracle repository. 

# 1. Clone the oracle repository on the oracle server
$ git clone https://github.com/javier20dev25/sentinel-oracle.git
$ cd sentinel-oracle

# 2. Install dependencies
$ npm install

# 3. Configure environment
$ cp .env.example .env
$ nano .env
#   GITHUB_TOKEN=ghp_xxxxxxxx              # Personal access token with merge permission
#   GITHUB_OWNER=my-org                     # GitHub org or user
#   GITHUB_REPO=my-repo                     # Repository name
#   TAILSCALE_HOST=oracle-server.tailnet.ts.net  # MagicDNS hostname
#   PORT=3000                               # Local port (tailscale listens)
#   DB_PATH=~/.sentinel-oracle/oracle.db    # SQLite database path

# 4. Build
$ npm run build

# 5. Start the daemon
$ npm start
# [oracle] Listening on http://0.0.0.0:3000
# [oracle] Tailscale: http://oracle-server.tailnet.ts.net:3000
# [oracle] Polling GitHub for PRs every 10s
# Dashboard

The oracle dashboard is a web interface served directly by the oracle server. It is accessible only from devices on the same Tailscale network. No authentication is needed at the dashboard level because Tailscale device identity and ACLs provide sufficient access control. Merge authorization always requires a separate WebAuthn assertion from a registered phone.

Dashboard Endpoints

Route Purpose Access
/dashboard Pending PRs with Authorize buttons Workstation + phone (Tailscale ACL)
/health JSON health check (status, uptime, version) Any Tailscale device
/devices Registered authenticators, revoke buttons Admin only (oracle server console)
/audit Audit trail: all merge operations with timestamps Admin only (oracle server console)
/register/:token Device registration page (WebAuthn prompt) Phone (TTL-limited token)
/authorize QR challenge verification (POST) Phone (challenge-bound)
# CLI Reference

The oracle server includes an administrative CLI for managing devices, lockdown state, and configuration. These commands run directly on the oracle server.

Command Description
sentinel oracle admin status Server status, uptime, pending PRs, device count
sentinel oracle admin register-device --name "label" Generate registration URL for a new phone
sentinel oracle admin revoke-device <id> Remove a registered device from the registry
sentinel oracle admin list-devices Show all registered authenticator devices
sentinel oracle admin lockdown enable Activate emergency lockdown
sentinel oracle admin lockdown disable Deactivate emergency lockdown (local console only)
sentinel oracle admin audit-log View the last 100 audit trail entries
sentinel oracle admin config show Display current configuration (secrets masked)
# Security Considerations

Threat Model

  • Compromised workstation: Attacker can view dashboard but cannot authorize merges. No merge credentials stored on workstation.
  • Compromised oracle server: Attacker has merge credentials. Mitigation: physical access required, Tailscale ACL limits inbound, audit trail logs all actions.
  • Lost phone: Revoke device from admin dashboard. QR challenges bound to PR number prevent replay.
  • Tailscale compromise: Tailscale uses WireGuard with rotating keys. Device identity is tied to Tailscale auth keys.

Data at Rest

  • GitHub token: stored in environment variable, not in database
  • WebAuthn credential public keys: stored in SQLite (not secrets -- public keys only)
  • HMAC signing keys: generated at startup, stored in SQLite with file permissions 0600
  • Audit log: append-only, stored in SQLite. No delete endpoint exists.
  • SQLite database: default location ~/.sentinel-oracle/oracle.db

Network Security

  • Zero public ports. All traffic over Tailscale WireGuard mesh.
  • No TLS termination on oracle server (handled by Tailscale's end-to-end encryption).
  • HTTP-only (Tailscale provides transport encryption equivalent to TLS).
  • Optional: deploy a reverse proxy (Caddy, nginx) for TLS termination within tailnet.

Audit Trail

  • Every merge authorization attempt is logged
  • Fields: timestamp, PR number, device ID, challenge hash, outcome (success/failure)
  • Lockdown activation/deactivation logged with console session ID
  • Device registration/revocation logged with admin session ID
  • Logs are append-only (no deletion). Back up SQLite for compliance.
